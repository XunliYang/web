# 社区导师制流程与规范

---

## 第一章 总则

### 1.1 目的

建立公司内部社区导师培养机制，通过专家带新人的方式，帮助员工快速融入真实开源项目，提升团队开源贡献能力和规范意识。

### 1.2 适用范围

本规范适用于：
- 新入职员工（加入公司 ≤ 6个月）
- 现有开发人员（已有工作经验但开源参与经验不足）

### 1.3 术语定义

| 术语 | 定义 |
|------|------|
| 导师 | 经认证的、在开源项目中有贡献经验的指导人员 |
| 学员 | 参与导师培养计划、接受指导的员工 |
| 培养周期 | 导师指导学员的时间周期，固定为6个月 |
| 认证委员会 | 负责导师认证评审的决策机构 |

## 第二章 导师管理

### 2.1 导师资格认证

#### 2.1.1 准入标准

导师认证需同时满足技术能力与软技能要求：

**初级导师标准：**
| 维度 | 要求 |
|------|------|
| 技术能力 | 在目标开源项目有 ≥ 3 个 merged PR |
| 软技能 | 能清晰表达技术概念 |

**高级导师标准：**
| 维度 | 要求 |
|------|------|
| 技术能力 | 熟悉项目核心模块，获得 Comitter/Maintainer 认可 |
| 软技能 | 能进行 Code Review 并给出建设性反馈，有过指导他人经验 |

#### 2.1.2 认证流程

1. **申请阶段**：员工自荐或团队推荐，填写《导师申请表》
2. **材料提交**：提交贡献记录、技术博客、指导案例等证明材料
3. **委员会评审**：认证委员会（技术主管 + 资深导师代表）评审申请
4. **认证颁发**：评审通过后颁发导师认证证书（分初级/高级两级）

### 2.2 导师池维护

#### 2.2.1 导师档案

每位认证导师建立档案，记录：
- 擅长领域与技术栈
- 目标开源项目及贡献情况
- 可指导人数上限（默认为2）
- 当前指导状态（空闲/在指导）

#### 2.2.2 动态调整

- **重新认证**：每半年进行一次重新认证
- **降级机制**：连续两个培养周期无指导记录，导师等级降级
- **退出机制**：导师可主动申请退出，或因违反规范被取消资格

### 2.3 导师激励

#### 2.3.1 荣誉激励

- 颁发导师认证证书
- 公司内部表彰通报
- 年度优秀导师评选

#### 2.3.2 物质激励

- 每季度指导津贴（具体标准由人力资源部门另行制定）
- 绩效考核加分
- 晋升通道优先考虑

## 第三章 学员管理与配对

### 3.1 学员筛选

学员筛选由组织统一负责，筛选依据：
- 项目需求与人员规划
- 员工参与开源项目的意愿
- 员工技术基础与学习潜力

### 3.2 配对流程

```
组织筛选学员 → 根据技术栈/项目需求匹配导师 → 正式建立指导关系 → 登记存档
```

#### 3.2.1 配对原则

- 一位导师同时指导不超过 2 名学员
- 优先考虑技术栈匹配度
- 优先考虑导师对目标项目的熟悉程度

#### 3.2.2 配对登记

配对完成后，填写《学员登记表》，记录：
- 学员基本信息
- 配对导师信息
- 目标开源项目
- 培养周期起止时间

---

## 第四章 培养周期管理

### 4.1 周期定义

- **培养周期长度**：6个月
- **周期起止**：以配对登记日期为准

### 4.2 评审节点

| 时间点 | 评审类型 | 评审内容 |
|--------|----------|----------|
| 第3个月 | 中期评审 | 进度评估、是否继续培养 |
| 第6个月 | 结项评审 | 是否达标、是否成为导师候选人 |

### 4.3 沟通机制

#### 4.3.1 沟通频率

- 最低频率：每两周至少 1 次正式沟通
- 沟通形式：线下交流、线上会议均可

#### 4.3.2 沟通记录

每次正式沟通后，导师填写《沟通记录表》，记录：
- 沟通时间与形式
- 学员进度情况
- 主要讨论内容
- 下一步行动计划

### 4.4 退出机制

| 情况 | 处理方式 |
|------|----------|
| 提前达标 | 学员提前达到结项标准，可申请提前结项 |
| 中期不达标 | 中期评审认定学员不适合继续，可中途退出 |
| 导师退出 | 导师因特殊情况无法继续指导，由组织协调更换导师 |

## 第五章 评审标准

### 5.1 评审维度

| 维度 | 权重 | 评审内容 | 评分依据 |
|------|------|----------|----------|
| 代码贡献 | 40% | PR数量、代码质量、合并情况 | PR数量、代码评审反馈、合并率 |
| 社区参与 | 30% | Issue参与、Code Review、社区会议 | Issue评论数、Review参与次数、会议参与次数 |
| 技术成长 | 20% | 技术栈掌握程度、独立解决问题能力 | 导师评估、任务完成情况 |
| 文档产出 | 10% | 技术文档、知识分享 | 文档数量、分享次数 |

### 5.2 结项标准

#### 5.2.1 通过标准

- 各维度得分 ≥ 60分
- 至少有 1 个 merged PR

#### 5.2.2 优秀标准

- 各维度得分 ≥ 80分
- 有 ≥ 2 个 merged PR
- 可作为导师候选人，进入下一期导师认证流程

### 5.3 评审流程

1. **材料提交**：学员提交结项材料（PR/MR链接、贡献记录、总结报告）
2. **导师评审**：导师填写《结项评审表》，提供评审意见
3. **委员会审核**：评审委员会审核确认评审结果
4. **结果公布**：正式公布评审结果，归档存档

## 第六章 导师与学员职责

### 6.1 导师职责

| 职责类型 | 具体内容 |
|----------|----------|
| 技术指导 | 解答技术问题、协助理解代码架构、Review代码 |
| 流程指导 | 指导PR规范、社区沟通方式、贡献流程 |
| 进度跟踪 | 定期沟通、记录学员进度、及时上报问题 |
| 评审参与 | 参与中期评审、结项评审、提供评审意见 |

### 6.2 学员职责

| 职责类型 | 具体内容 |
|----------|----------|
| 学习实践 | 按计划完成学习任务、积极提交PR |
| 主动沟通 | 主动向导师汇报进度、提出问题 |
| 社区参与 | 参与社区讨论、遵守社区规范 |
| 文档记录 | 记录学习过程、撰写结项报告 |

## 第七章 组织管理与支持

### 7.1 组织角色

#### 7.1.1 管理委员会

职责：
- 制定导师制相关政策
- 导师认证评审决策
- 结项评审最终确认
- 资源协调与保障

组成：技术主管 + 资深导师代表（至少2人）

#### 7.1.2 项目协调人

职责：
- 学员筛选与登记
- 导师匹配与配对
- 进度跟踪与督促
- 问题协调与解决

### 7.2 支持机制

#### 7.2.1 培训支持

| 对象 | 培训内容 |
|------|----------|
| 导师 | 指导技巧、沟通方法、评审规范 |
| 学员 | 开源贡献流程、社区规范、PR提交规范 |

#### 7.2.2 工具支持

- 沟通平台：公司内部沟通工具（如企业微信、飞书等）
- 进度跟踪：项目管理工具（如Jira、Trello等）
- 贡献记录：GitHub/GitCode 贡献统计

#### 7.2.3 时间支持

- 导师指导时间计入工作量
- 学员有固定的学习与实践时间
